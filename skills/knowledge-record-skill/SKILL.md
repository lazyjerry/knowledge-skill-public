# 知識沉澱

把已驗證、換到別的專案仍成立的結論，寫進共用知識庫（預設 `$HOME/.knowledge-skill/knowledge/`，可用 `KNOWLEDGE_BASE_DIR` 覆寫），讓後續任務能先查索引、不必重查。

> ⚠️ **未取得使用者明確同意（含步驟 4 的明確要求保存、本 session 概括同意），絕不寫入知識庫。** 本 skill 可由模型自動觸發，這條是安全邊界。例外只有兩種，條件與限制寫在各自的步驟，不得擴大解釋：
>
> - 步驟 4 的**免詢問自動收錄**：五條閘門全過的全新知識，狀態標為 `AI 自動確認`，每次回報，使用者可關閉。
> - 步驟 6 的**過時、錯誤改寫**：附屬於一次使用者已同意的記錄。

## 職責邊界

本 skill 只負責兩件事：**判斷什麼值得記**、**把結論寫成 MADR 內容**。其餘固定流程一律呼叫腳本，不自行實作：

| 要做的事 | 呼叫 | 不要自己做 |
|---|---|---|
| 檢查知識庫是否就緒 | `sh <TOOLS>/kb-status.sh` | 自行讀 `index.md` 判斷結構完整性 |
| 產生知識草稿 | `sh <TOOLS>/kb-new.sh <相對路徑>` | 憑記憶拼 MADR 骨架、自行檢查是否已存在 |
| 安裝草稿為生效知識 | `sh <TOOLS>/kb-promote.sh <草稿> <相對路徑> --yes --source <來源>`（免詢問自動收錄把 `--yes` 換成 `--auto`） | 直接寫入知識庫、另外呼叫 reindex、手填 `狀態` |
| 取代被淘汰的知識 | `sh <TOOLS>/kb-supersede.sh <舊> <新> --yes` | 自行把舊檔移進 `deprecated/` |
| 移除誤建的知識 | `sh <TOOLS>/kb-delete.sh <路徑> --yes` | 直接刪檔（索引會斷鏈） |
| 合併、改寫既有知識 | 編輯該知識檔後 `sh <TOOLS>/kb-reindex.sh` | 手改任何 `index.md` |
| 查詢、切換自動收錄開關 | `sh <TOOLS>/kb-auto.sh status`／`on --yes`／`off --yes` | 自行讀寫設定檔 |
| 把自動收錄的知識改為人工審核確認 | `sh <TOOLS>/kb-auto.sh confirm <相對路徑>... --yes`（全部：`confirm --all --yes`） | 手改 front matter 的 `狀態` |

合併與改寫是唯一由代理直接編輯知識檔的情況（沒有對應的安裝腳本），只限步驟 5 的同主題合併與步驟 6 的直接改寫。

`<SKILL_DIR>` 為此 skill 的安裝目錄，`<TOOLS>` = `<SKILL_DIR>/../knowledge-tools-skill/scripts`。

**靜態資料同樣不重複**——MADR 範本與收錄判準的單一規範來源都在 `knowledge-skill`：

- 範本：`knowledge-skill/assets/knowledge.md`，由 `kb-new.sh` 取用，本檔不留副本。
- 完整收錄判準：`knowledge-skill/references/knowledge-base.md` 的「三、何時產生知識檔案」；本檔只留下方的速判規則，拿不準時才讀完整版。

因此三個 skill（`knowledge-skill`、`knowledge-record-skill`、`knowledge-tools-skill`）需並存安裝。

**建檔交給 subagent**：判斷候選與徵詢同意留在主對話，步驟 5 的建檔與步驟 6 的矛盾比對交給 subagent，分工與交派方式見 [references/delegate.md](references/delegate.md)。

## 原生互動選單路由

需要使用者裁決的固定選項（步驟 4 的記錄同意、步驟 6 的取代決策），依**目前可用工具**選擇呈現方式，不只依賴模式名稱：

1. **Claude Code**：`AskUserQuestion` 可用時必須呼叫，VSCode extension 顯示可點選對話框，CLI 顯示 TUI 選擇器。
2. **Codex**：`request_user_input` 可用時必須呼叫；Plan mode 預設提供，Default mode 只有在 client 提供該工具時可用（例如使用者自行啟用實驗性的 `default_mode_request_user_input`）。
3. **原生工具不可用**：說明目前 client 不支援原生選單，再退回編號清單，讓使用者回覆編號。

共通限制：

- 每題最多三個固定選項（步驟 4 多項候選那題例外，為四個）；較大選單拆成兩層，無上限清單以「選擇此項／下一項／取消」逐筆瀏覽。
- 原生工具可用時，不得要求使用者輸入固定選項的編號、label 或命令名。
- 只有選擇「自行輸入／自訂／要求調整」後，才要求自由文字，例如票號、路徑、檔名或修改意見。
- 每個選項包含簡短 label 與一行影響說明，建議選項排第一。
- VSCode integrated terminal 仍屬 CLI TUI，不宣稱會顯示 extension panel 的圖形按鈕。
- `claude -p`、`codex exec` 等非互動模式不承諾顯示選單。
- 本 skill 不自動修改 client feature、不安裝 MCP 或 Plugin。

## 主流程

### 1. 前置檢查：知識庫是否就緒

```bash
sh <TOOLS>/kb-status.sh
```

結束碼 1（缺目錄或缺 `index.md`）→ **停止，不自行建立**，提示使用者先執行 repo 的 `scripts/init-knowledge-base.sh` 或啟動 `/knowledge-skill`。先擋掉可省下無效建檔。結束碼 2（有斷鏈、孤兒，或索引仍是舊的單層結構）不影響建檔，照常繼續。

### 2. 判定來源

| 入口 | 情境 | 來源 |
|------|------|------|
| A | 呼叫端提供任務資料夾（例如由 `knowledge-skill` 呼叫） | 該資料夾的 `notes.md` 與 `report-<任務名稱英文>.md` |
| B | 無任務資料夾（模型自動觸發） | 本次對話中已驗證的結論 |

### 3. 判斷候選

提示：`🤔 正在評估是否有知識需記錄...`

速判三問，全過才是候選：

1. **換到別的專案是否仍成立？** 只對當前專案成立的細節（特定檔案路徑、特定服務設定）不算。
2. **是結論還是流水帳？** 「本次改了哪些檔案、跑了哪些指令、依序做了哪些步驟」是過程紀錄，屬於任務資料夾的 `notes.md`。只有能改寫成「下次遇到同情境該怎麼做」的才算；改寫不出來就丟掉。
3. **是否已在別處寫過？** 一般程式設計知識、框架標準用法、官方文件已說明的內容不收。

使用者說「記住」「以後都這樣做」「這個要記下來」時，直接視為候選，且視為已同意（見步驟 4）。拿不準時讀 `knowledge-skill/references/knowledge-base.md` 的「三、何時產生知識檔案」。

**無候選時**：

- 入口 A → 輸出 `📚 本次任務無需記錄新知識`
- 入口 B → **安靜結束，不輸出任何訊息**（自動觸發不該在每次任務結束打斷使用者）

### 4. 徵詢使用者

先收斂再問：同主題的多筆候選合併成一則，不拆成多則。

每則候選依序判斷，前一項成立就不看後面：使用者明確要求保存 → 本 session 概括同意仍有效 → 免詢問自動收錄的五條閘門全過 → 以上都不是才徵詢。各項的條件見本步驟後面的區塊。

- 只有一項 → 詢問「記錄／略過／本 session 都記錄」。
- 有多項 → 先詢問「全部記錄／逐項決定／全部略過／本 session 都記錄」。
- 逐項決定 → 每項依序詢問「記錄此項／下一項／取消」，不要求輸入編號。「下一項」＝略過此項、繼續問下一項；「取消」＝停止詢問，已選「記錄此項」的照記，尚未問到的全部略過。
- 原生工具不可用 → 列出候選（`k1`、`k2`、`k3`）並退回文字編號 fallback。

每個候選呈現時附一行摘要，讓使用者知道自己同意的是什麼。

**本 session 都記錄**（概括同意）：

- 本次的候選全部記錄；本 session 之後的候選視為已同意，跳過步驟 4 直接進步驟 5。
- 只涵蓋步驟 4 的記錄同意；步驟 6 遇到衝突仍每次詢問。
- 不靜默寫入：每次寫入照樣輸出步驟 7 的回報（入口 B 也是）。
- 失效：開新 session、context 經過 compaction、或使用者表示撤回（例如「之後先問我」）後，回到逐次詢問。判斷方式：目前 context 裡看得到使用者當時選了「本 session 都記錄」才算有效；只剩摘要轉述、或無法確定時視為失效。
- 是否有效只由主代理判斷；subagent 不繼承、不自行判斷。
- 原生工具不可用時，文字 fallback 同樣列出這個選項。

**使用者明確要求保存**（「記住」「以後都這樣做」「這個要記下來」等）：

- 視為同意，不跳選單，直接進步驟 5。
- 沒講記在哪裡也照記：auto memory、施工筆記由各自的機制記錄，共用知識庫同樣要記，不詢問要記到哪裡。
- 只有「這個」指向哪則不明時才詢問，選項列出可能的候選。
- 代理另外判斷出的候選，不在使用者指名的範圍內，照常徵詢。
- 使用者指名的內容過不了步驟 3 的速判三問時，以使用者的要求為準、照記：只對單一專案成立的，在 `觸發時機` 寫明適用範圍；流水帳先改寫成「下次遇到同情境該怎麼做」再記，改寫不出來才不記，並告知原因。

**免詢問自動收錄**（預設開啟，使用者可關閉）：

代理自己判斷出的候選，下列五條**全過**就不徵詢，直接進步驟 5 並以 `--auto` 安裝；任一條不過、或拿不準，照上面的選單徵詢。

| # | 條件 | 判定方式 |
|---|---|---|
| 1 | 全新、無重複 | `kb-new.sh` 沒擋下，且同分類找不到相同觸發情境的知識（`sh <TOOLS>/kb-reconcile.sh <分類前綴>`）；需要合併或改寫既有知識、或與既有知識衝突的都不算 |
| 2 | 跨專案通用 | 不同專案、不同程式都會碰到；`觸發時機` 以技術或情境描述，全文不出現專案名稱、專案路徑、內部網址 |
| 3 | 本次實際驗證過 | `## 驗證` 寫得出驗證方式與結果；只是推論、沒跑過的不算 |
| 4 | 沒有這則脈絡會做錯 | 寫得出「一般會以為怎樣、實際上怎樣」；官方文件已寫明的不算 |
| 5 | 不含敏感內容 | 關鍵規則 9 |

- **先確認開關**：`sh <TOOLS>/kb-auto.sh status`。顯示關閉時整段跳過，候選全部照常徵詢。使用者說「關閉自動收錄」→ `sh <TOOLS>/kb-auto.sh off --yes`；「開啟自動收錄」→ `on --yes`（使用者的要求即同意）。
- **範圍只到新增**：合併、改寫、取代都不走這條通道。
- **安裝帶 `--auto`、不帶 `--yes`**：腳本把狀態寫成 `AI 自動確認`、來源加上「自動收錄：」前綴，並自行檢查開關與 `## 驗證` 段。腳本拒絕時（結束碼 3：開關關閉；結束碼 1：驗證段沒有內容）改為徵詢，不得改帶 `--yes` 硬裝。
- **數量上限**：同一次任務最多自動收錄 10 則（一次任務內多次啟動本 skill 時累計）；超過的照常徵詢。
- **不靜默寫入**：每次都輸出步驟 7 的回報（入口 B 也是）。
- **由主代理判定**：條件 2–5 與 10 則的計數都在主代理。交派給 subagent 時，subagent 只複核條件 1，不過就不寫入、回報給主代理徵詢；subagent 不得自行把候選改成免詢問。
- **已有使用者同意的不走這條**：明確要求保存、概括同意、選單同意的候選照常以 `--yes` 安裝，狀態為 `人工審核確認`。

### 5. 建檔

> 能派出 subagent 時，本步驟與步驟 6 的比對依 [references/delegate.md](references/delegate.md) 交派，主代理收到回報後接步驟 6 的徵詢。以下內容同時是 subagent 的執行規則，也是無法交派時主代理自己執行的流程。

**決定分類與路徑**（這是判斷，不是固定流程，由代理決定後傳給腳本）：

- 頂層分類（6 類）：`ui`／`ux`／`dev`／`ops`／`data`／`else`。
- 第二層依語言／框架／平台細分，例如 `dev/php-laravel/`、`dev/ai-llm/`、`ops/cloudflare/`。
- 路徑形如 `{分類}/{語言-框架}/[topic].md`；無合適第二層時可直接放分類根（如 `else/[topic].md`）。
- 相同主題**合併進既有知識檔**（直接編輯該檔後執行 `sh <TOOLS>/kb-reindex.sh`），不重複建檔。合併不經 `kb-promote.sh`，來源要自己留：在該檔 `## 補充資訊` 加一行 `YYYY-MM-DD 合併：<來源說明>`。

**新主題**依序執行：

```bash
# 1. 產生草稿（會擋掉路徑不合法與目標已存在；最後一行輸出草稿路徑）
sh <TOOLS>/kb-new.sh <分類>/<語言-框架>/<topic>.md

# 2. 代理填寫草稿內容（見下方填寫規則）

# 3. 安裝：驗證格式、拒絕覆蓋、原子寫入並自動重建索引
sh <TOOLS>/kb-promote.sh <草稿路徑> <分類>/<語言-框架>/<topic>.md --yes --source "<來源說明>"
```

`--yes` 代表**已於步驟 4 取得使用者同意**；未取得同意不得帶。免詢問自動收錄的候選把 `--yes` 換成 `--auto`（代表步驟 4 的五條閘門全過，兩者不可並用），其餘情況不得帶 `--auto`。`--source` 填來源：入口 A 填任務資料夾路徑，入口 B 填對話來源說明——草稿的暫存路徑沒有追溯價值。

**填寫規則**（欄位語意，格式本身由範本與腳本保證）：

- `標題` 與 `觸發時機` 不可留範本佔位（`[...]` 開頭），`kb-promote.sh` 會擋下。
- `觸發時機` 與 `## 摘要` 的**第一行**就要寫清楚：`kb-reindex.sh` 只取這兩處生成索引欄位。
- `取代`／`被取代於` 保持 `-`，由 `kb-supersede.sh` 維護，勿手填。
- `狀態` 由 `kb-promote.sh` 寫入（`--yes` → `人工審核確認`；`--auto` → `AI 自動確認`），草稿裡填什麼都會被覆寫，勿手填。
- `決策驅力`、`各選項利弊`、`驗證` 沒內容就保留一行 `-`；免詢問自動收錄的候選 `## 驗證` 必須寫明驗證方式與結果。
- 入口 A 時在 `## 補充資訊` 記錄來源任務資料夾。
- 知識庫跨專案共用，內容不寫入機密（密碼、token、金鑰）、裝置的絕對路徑、工作用的專案名稱與內部網址；需要舉例時改用 `<專案路徑>` 這類佔位。`--source` 與 `## 補充資訊` 的任務資料夾只寫資料夾名稱或專案根的相對路徑——`kb-promote.sh` 會把 `--source` 原樣寫進知識檔。
- 草稿放棄不安裝時（腳本擋下且不修正、候選作廢），刪掉 `kb-new.sh` 產生的草稿目錄。

提示：`📚 正在建立公用知識檔案：knowledge/<相對路徑>`

### 6. 新舊矛盾

比對新知識與既有知識（可先用 `sh <TOOLS>/kb-reconcile.sh [分類前綴]` 列出生效知識），依性質處理：

| 性質 | 判斷 | 處理 |
|---|---|---|
| 過時 | 本次已驗證的事實顯示舊結論不再適用（工具版本、介面、做法已改變） | 不詢問，直接改寫，步驟 7 回報 |
| 錯誤 | 本次有驗證證據顯示舊結論本來就不成立 | 不詢問，直接改寫，步驟 7 回報 |
| 衝突 | 同一觸發情境兩者給出不同決策、各有取捨，無法用事實判定對錯 | 依原生路由詢問「以新知識取代／保留舊知識」，**取得同意後**才執行 `kb-supersede.sh` |

拿不準屬於過時、錯誤還是衝突時，當衝突處理。

**衝突的兩種結果**（新檔在步驟 5 已建立）：

- 以新知識取代 → `sh <TOOLS>/kb-supersede.sh <舊檔相對路徑> <新檔相對路徑> --yes`。
- 保留舊知識 → 移除剛建的新檔：`sh <TOOLS>/kb-delete.sh <新檔相對路徑> --yes`（使用者的選擇即同意），步驟 7 回報該則未記錄；不讓兩則互相矛盾的知識並存。

**直接改寫的條件**（過時、錯誤；這是「未同意不寫入」的唯一例外）：

- 只在一次已同意的記錄中附帶發生，不為了改寫舊知識而單獨啟動。免詢問自動收錄的記錄沒有使用者同意，不附帶改寫：這時發現舊知識過時或錯誤，一律當衝突徵詢。
- 要有本次驗證的事實佐證，且寫得出是哪一項事實；只是推測、或佐證不在手上（例如 subagent 的候選「依據」沒寫到），當衝突處理。
- 只動被推翻的結論，不順手改寫同一檔的其他內容。
- 每次都在步驟 7 回報，使用者不同意時依留下的原結論改回。

**直接改寫**（過時、錯誤）：

- 同主題：新結論寫進舊檔，不另建新檔；標題、觸發時機、摘要第一行一併更新。
- 已另建新檔、只推翻舊檔部分結論：改寫舊檔中過時或錯誤的段落。
- 兩種都在舊檔 `## 補充資訊` 加一行 `YYYY-MM-DD 改寫：<過時／錯誤>，原結論為 <原摘要第一行與原決策結果，照錄不濃縮>`，再執行 `sh <TOOLS>/kb-reindex.sh`。知識檔沒有備份機制，這一行是唯一的還原依據。
- 舊檔整份不成立：直接取代，不詢問（腳本會寫入取代關係、把舊檔移入 `deprecated/` 並重建索引，舊檔內容完整保留）：

```bash
sh <TOOLS>/kb-supersede.sh <舊檔相對路徑> <新檔相對路徑> --yes
```

交派給 subagent 時，過時、錯誤的**段落改寫**由 subagent 執行並回報；`kb-supersede.sh` 與 `kb-delete.sh` 一律由主代理執行——整份不成立的由 subagent 回報「取代建議」、主代理直接執行，衝突由主代理徵詢後執行。

### 7. 回報

每則一行：知識庫內的相對路徑（看得出在哪個資料夾）加摘要第一行（看得出記了什麼）；標題行給知識庫位置。

使用者同意後記錄的：

```
📝 已記錄 2 則｜知識庫：~/.knowledge-skill/knowledge/
- dev/shell/<檔名>.md — <摘要第一行>
- ops/docker/<檔名>.md — <摘要第一行>
✏️ 已改寫既有知識：dev/git/<檔名>.md（過時／錯誤：一句話說明）
🗑️ 不要的請說「刪除知識 <路徑>」
```

免詢問自動收錄的：

```
📝 已自動收錄 2 則（AI 自動確認）｜知識庫：~/.knowledge-skill/knowledge/
- dev/shell/<檔名>.md — <摘要第一行>
- ops/docker/<檔名>.md — <摘要第一行>
✅ 沒問題的請說「確認知識 <路徑>」或「確認全部自動收錄的知識」
🗑️ 不要的請說「刪除知識 <路徑>」
```

- 知識庫位置取步驟 1 `kb-status.sh` 輸出的「路徑」那行（`~` 開頭的顯示形式），不貼裝置的絕對路徑。
- 同一次兩種都有時各列一段，知識庫位置只在第一段的標題行出現，🗑️ 那行只在最後出現一次。
- 沒有改寫就省略 ✏️ 那行；整份取代的寫 `<舊檔路徑> → <新檔路徑>（過時／錯誤：一句話說明）`。
- 衝突後選擇保留舊知識的，另列一行 `↩️ 未記錄：<路徑>（與既有知識衝突，已保留舊知識）`。

使用者的後續要求（要求即同意；代理執行沒有 tty，不帶 `--yes` 會以結束碼 3 中止；兩支腳本都會自動重建索引）：

- 「刪除知識 <路徑>」→ `sh <TOOLS>/kb-delete.sh <相對路徑> --yes`，不手動刪檔。
- 「確認知識 <路徑>」→ `sh <TOOLS>/kb-auto.sh confirm <相對路徑> --yes`；「確認全部自動收錄的知識」→ `sh <TOOLS>/kb-auto.sh confirm --all --yes`。狀態由 `AI 自動確認` 改為 `人工審核確認`，不手改 front matter。

## 關鍵規則

| # | 規則 |
|---|------|
| 1 | 未取得使用者明確同意（逐次、明確要求保存或本 session 概括同意），絕不寫入知識庫；`--yes` 代表同意已取得。例外只有步驟 4 五條閘門全過的免詢問自動收錄（`--auto`）與步驟 6 符合條件的過時、錯誤改寫，兩者事後必回報 |
| 2 | 建檔、安裝、取代、刪除、索引一律由 `<TOOLS>` 的腳本執行，代理只填內容與決定分類；直接編輯知識檔只限同主題合併與步驟 6 的改寫 |
| 3 | 不手動編輯任何 `index.md`；`kb-promote.sh`／`kb-supersede.sh`／`kb-delete.sh` 已自動重建 |
| 4 | 只收跨專案可重用的結論；單一專案細節、一般常識、一次性結果、變更流水帳不寫入 |
| 5 | 範本與完整判準以 `knowledge-skill` 為單一來源，本檔不留副本 |
| 6 | 自動觸發且無候選時安靜結束，不打斷使用者 |
| 7 | 原生選單工具可用時使用原生 UI，不可用才退回文字編號 |
| 8 | 徵詢與免詢問的判定只在主對話；交派的 subagent 只處理主代理交付的候選，不徵詢、不自行把候選改成免詢問、不執行 `kb-supersede.sh` 與 `kb-delete.sh` |

| 10 | 免詢問自動收錄只限全新知識，同一次任務最多 10 則；開關關閉、腳本拒絕或拿不準時一律改為徵詢 |
| 11 | `狀態` 只由 `kb-promote.sh` 與 `kb-auto.sh` 寫入，不手填、不手改 |
