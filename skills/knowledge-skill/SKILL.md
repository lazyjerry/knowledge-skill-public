# 檔案式任務規劃

用持久性 markdown 檔案作為「磁碟上的工作記憶」。

> 💡 **目標導向**：除了產生報告，最終目的是把驗證過、跨專案成立的發現上提到共用 `knowledge/`，讓後續任務能直接查閱、不必重查。

## 原生互動選單路由

所有需要使用者裁決的固定選項，依**目前可用工具**選擇呈現方式，不只依賴模式名稱：

1. **Claude Code**：`AskUserQuestion` 可用時必須呼叫，VSCode extension 顯示可點選對話框，CLI 顯示 TUI 選擇器。
2. **Codex**：`request_user_input` 可用時必須呼叫；Plan mode 預設提供，Default mode 只有在 client 提供該工具時可用（例如使用者自行啟用實驗性的 `default_mode_request_user_input`）。
3. **原生工具不可用**：說明目前 client 不支援原生選單，再退回編號清單，讓使用者回覆編號。

共通限制：

- 每題最多三個固定選項；較大選單拆成兩層，無上限清單以「選擇此項／下一項／取消」逐筆瀏覽。
- 原生工具可用時，不得要求使用者輸入固定選項的編號、label 或命令名。
- 只有選擇「自行輸入／自訂／要求調整」後，才要求自由文字，例如票號、路徑、檔名或修改意見。
- 每個選項包含簡短 label 與一行影響說明，建議選項排第一。
- VSCode integrated terminal 仍屬 CLI TUI，不宣稱會顯示 extension panel 的圖形按鈕。
- `claude -p`、`codex exec` 等非互動模式不承諾顯示選單。
- 本 skill 不自動修改 client feature、不安裝 MCP 或 Plugin。

## 任務開始前

0. **決定任務名稱與報告英文名稱**（詳細規範見 `references/file-structure.md` 的「任務命名規則」）：
   - 任務名稱使用**繁體中文**，簡短描述任務目的。
   - 名稱中的空格與特殊符號一律以底線 `_` 取代，避免資料夾／檔案名稱損毀。
   - 同時把任務名稱翻成**網址式 kebab-case 英文 slug**（只有小寫英文、數字與單一連字號），決定報告檔名 `report-<slug>.md`。例：`AI_工具記憶優化` → `ai-memory-optimization` → `report-ai-memory-optimization.md`。此項由代理自行翻譯，不另外詢問使用者。

1. **啟動提問（先給預設摘要，再以選單逐項調整）**：執行初始化腳本前，先彙整五題的預設值並用**選單**詢問；**不要**要求使用者用一段自由文字一次回覆全部設定（細節與選項規範見 `references/rules.md` 的「啟動提問與計畫確認」）：

   1. **彙整預設值**：先嘗試從 git 分支、目錄或上下文**推斷**票號、讀取工作區 `git config user.name` 作為作者，整理五題預設：
      - 票號：〔推斷票號：`<推斷值>`〕；無法推斷則為「沒有票號」
      - 執行模式：一次完成
      - 報告保存路徑：`<工作區>/docs/knowledge-skill/<任務名稱>-<流水號>/`
      - 研究計畫：不先確認
      - 作者：〔git user.name：`<值>`〕；讀不到則為「自行輸入」
   2. **單一選單詢問是否調整**（選單中同時顯示上述預設摘要）：
      - **全部採用預設** → 直接採用，進入步驟 2。
      - **逐項調整** → 對下列五題逐一依「原生互動選單路由」詢問；固定選項不得要求打字，只有選擇自訂後才收自由文字：
        1. **票號／編號**（決定任務名稱前綴）：〔推斷票號：`<推斷值>`〕（僅能推斷時提供）／沒有票號／自行輸入票號。有票號則組成 `票號-任務名稱`，例如 `T-0001-AI_工具記憶優化`。
        2. **執行模式**（任務複雜或需跨多個觀察系統研究時尤其重要）：(A) 一次完成 / (B) 分階段執行 / (C) 部分執行。
        3. **報告保存路徑**：使用預設 / 自訂（自行輸入工作區路徑，作為下一步 `<工作區路徑>`）。
        4. **是否先確認研究計畫**：(否) 直接執行 / (是) 先在 `task_plan.md` 補上詳細研究動作計畫並等待確認，確認後才產出完整報告。
        5. **作者**（寫入報告 YAML meta）：〔git user.name：`<值>`〕（僅讀得到時提供）／自行輸入作者。

2. 執行初始化腳本（`<SKILL_DIR>` 為此 skill 的安裝目錄、`<工作區路徑>` 為步驟 1 之三決定的目標根目錄、`<任務名稱>` 為步驟 0／1 組合並轉換後的名稱、`<報告英文名稱>` 為步驟 0 決定的 slug）：
```bash
sh <SKILL_DIR>/scripts/init-session.sh <工作區路徑> <任務名稱> <報告英文名稱>
```

   > 腳本會驗證 `<報告英文名稱>` 的 kebab-case 格式，不合格即 `exit 1` 並印出規則；成功時最後一行印出完成時要建立的報告檔名。

   > ⚠️ **此腳本一開始就會建立／確認公用知識庫，並先驗證該路徑（預設或 `KNOWLEDGE_BASE_DIR`）可讀寫。** 依結束碼處理，**知識庫未就緒前不要進入後續步驟**，避免任務跑到後段才中斷：
   >
   > - **`exit 0`** → 知識庫就緒，繼續。
   > - **`exit 1`** → 參數／工作區錯誤，修正後重跑。
   > - **`exit 2`（路徑無法讀寫）** → 腳本已印出三個路徑選項。**停下來，依「原生互動選單路由」呈現三選一**，再依選擇重跑（重跑會自動重新驗證；仍失敗就再讓使用者選一次，直到 `exit 0`）：
   >   1. **維持原路徑，先開權限** → 依**目前所用的 AI 工具**轉達對應開法（Claude Code：`permissions.additionalDirectories`／`/add-dir`；Codex：`[sandbox_workspace_write].writable_roots`；Antigravity：`--add-dir`；Copilot：OS 權限）。使用者開好後，重新執行**相同指令**。
   >   2. **改用專案內路徑**（腳本會顯示該路徑，位於工作區、必定可寫，但知識庫不再跨專案共用）→ 以 `KNOWLEDGE_BASE_DIR="<專案內路徑>"` 重跑。
   >   3. **指定其他路徑** → 以 `KNOWLEDGE_BASE_DIR="<使用者指定路徑>"` 重跑。

3. 讀取必要參考文件：
   - `<SKILL_DIR>/references/file-structure.md` — 目錄結構、命名規則、範本
   - `<SKILL_DIR>/references/rules.md` — 完整規則與反模式
   - `<SKILL_DIR>/references/knowledge-base.md` — 知識庫使用規範
提示：`📖 正在讀取參考文件...`

4. 編輯範本檔案（**先讀取再編輯**，避免假設範本內容）：
   先讀取 `<任務資料夾>/prompt.md` 與 `<任務資料夾>/task_plan.md`。
   - `prompt.md` — 填入使用者輸入的原始提示詞、參考的資料
   - `task_plan.md` — 定義目標與階段、待辦項目，於「執行模式」記錄步驟 1 之二的選擇，並於「報告檔名」填入步驟 2 腳本印出的 `report-<slug>.md`（分階段任務跨 session 續作時據此沿用同一檔名）
   - `task_plan.md` 的「報告 meta」— 填入步驟 1 的票號、執行模式、研究計畫確認與作者；`日期` 留到建立報告時才填，`遠端連結` 留空
   - `notes.md` — （選填）記錄初步研究、決議
   
   > 取代文字時，舊字串必須與讀取到的實際內容完全一致。
   
5. 驗證檔案已編輯（自動插入階段檢核點，未通過則回到步驟 4）：
```bash
sh <SKILL_DIR>/scripts/validate-task-files.sh <任務資料夾路徑>
```

6. **研究計畫確認（僅當步驟 1 之四選擇「先確認」）**：在 `task_plan.md` 的「研究動作計畫」區塊補上具體的研究步驟與驗證點，依「原生互動選單路由」呈現「批准並繼續／要求調整」。**未取得確認前不要展開完整研究與報告**；選擇調整後才收自由文字，修改後再次確認，直到同意為止。詳見 `references/rules.md` 的「啟動提問與計畫確認」。

7. **報告路徑偏好沉澱（僅當步驟 1 之三更改了路徑）**：依「原生互動選單路由」詢問「記錄偏好／不記錄」。使用者同意才依「任務完成後」的知識建立流程記錄。

8. 告知使用者：
```
開始研究任務：［任務描述］
📁 任務資料夾：<報告保存路徑>/[任務名稱]-[流水號]/
執行模式：[一次完成 / 分階段 / 部分執行]
研究計畫確認：[需先確認 / 不需確認]
```

## 分階段任務：每次對話開始時

> 詳細規範見 `references/rules.md`

1. 讀取 `task_plan.md` 與 `notes.md`，確認進度與上下文
2. 提示目前狀態（已完成數、下一項目、上次進度摘要）
3. 依「原生互動選單路由」詢問「繼續下一階段／本次停止」，確認後繼續

## 每次重要動作/階段開始之前

1. 讀取公用知識庫**頂層**索引 `$KNOWLEDGE_BASE_DIR/index.md`（預設 `$HOME/.knowledge-skill/knowledge/index.md`，跨專案共用）——只有分類目錄與各分類知識標題
2. 有可能相關的分類，才讀該分類子索引 `{分類}/index.md`（完整觸發時機與摘要）；觸發時機相符才讀對應知識檔案
3. 提示使用者知識庫查閱結果：
   - 如有載入 → `📚 已參考公用知識庫：knowledge/XXX.md`
   - 如無匹配 → `📚 公用知識庫無相關項目`

## 每階段完成之後

**必須完成以下檢核清單（依序執行）：**

1. 更新 `notes.md`：記錄來源、發現與研究過程
2. 更新 `task_plan.md`：標記 [x]、更新狀態
3. 如有錯誤，記錄於 `task_plan.md` 的「遇到的錯誤」區塊

> ⚠️ **先更新 notes.md，再更新 task_plan.md**。

## 任務完成後

> 📝 **報告改寫**：`report-<slug>.md` 不是變更日誌。非首次變更時以**最後結論**改寫對應段落，不追加流水紀錄；意圖差異寫「結論變更」段落、與結論不衝突但使用者必須知道的事項寫「補充事項」段落。詳見 `references/rules.md` 的「報告改寫規範」。

> 🏷️ **報告 meta**：首次建立 `report-<slug>.md` 時，第一行起放 `task_plan.md`「報告 meta」區塊的 YAML front matter，`日期` 填當天；改寫報告時保留 meta 不動。欄位見 `references/file-structure.md` 的「報告 YAML meta」。

0. 驗證任務檔案完整性：
   - 必要檔案清單定義於 `<SKILL_DIR>/references/file-structure.md` 的 REQUIRED_FILES 變數
   - 執行驗證腳本：
     ```bash
     sh <SKILL_DIR>/scripts/validate-task-completion.sh <工作區路徑> <任務名稱-流水號>
     ```
   - 未通過則補齊缺少的檔案後重新驗證
1. **知識沉澱**：執行 `knowledge-record-skill`，把本次任務資料夾路徑作為來源。該 skill 讀取其中的 `notes.md`、`report-<任務名稱英文>.md`，判斷候選、以選單徵詢同意，再由 `kb-new.sh`／`kb-promote.sh` 建檔並重建索引；判準與格式同樣以 `references/knowledge-base.md` 為單一規範來源。
   - Claude Code：以 `Skill` 工具呼叫 `knowledge-record-skill`。
   - 其他工具：讀取 `<SKILL_DIR>/../knowledge-record-skill/SKILL.md`，依其流程執行。
2. 報告本次建立的知識檔案  
   提示：`📝 本次建立的知識檔案：[列表]`
3. **輸出報告路徑**：複述步驟 0 驗證腳本印出的兩行路徑，供使用者直接複製前往。路徑各自獨立成行，不加反引號或其他裝飾字元：
```
📄 報告路徑（可複製）：
<絕對路徑>/report-<任務名稱英文>.md
docs/knowledge-skill/<任務名稱-流水號>/report-<任務名稱英文>.md
```

> 💡 知識沉澱由 `knowledge-record-skill` 執行，知識庫的維運（重建索引、取代、盤點矛盾）由 `knowledge-tools-skill` 的腳本統一執行，假設三個 skill 並存安裝。

## 關鍵規則

| # | 規則 | 動作 |
|---|------|------|
| 0 | 檢查知識庫 | 每次重要動作前讀取公用頂層 `$KNOWLEDGE_BASE_DIR/index.md`，命中分類再讀 `{分類}/index.md` |
| 1 | 先建立計劃 | 絕不在沒有 `task_plan.md` 下開始 |
| 2 | 續作先讀 | 分階段任務每次對話開始時讀取 `task_plan.md` 與 `notes.md` |
| 3 | 行動後更新 | **先** `notes.md`，**再** `task_plan.md` |
| 4 | 儲存而非塞入 | 大量輸出寫入檔案 |
| 5 | 記錄錯誤 | 寫入計劃檔案的「遇到的錯誤」區塊 |
| 6 | 累積知識 | 任務結束時執行 `knowledge-record-skill`，把跨專案可重用經驗寫入公用知識庫 |
| 7 | 報告知識 | 結束時列出建立的知識檔案 |
| 8 | Git Ignore | 結束時提醒排除 `docs/knowledge-skill/` |
| 9 | 驗證完整 | 結束前執行 `validate-task-completion.sh` |
| 10 | 原生選單 | 工具可用時使用原生 UI；不可用才退回文字編號 |
| 11 | 回報報告路徑 | 結束時輸出 `report-<任務名稱英文>.md` 的絕對與專案相對路徑 |
| 12 | 報告以結論為準 | 改寫報告時保留最後結論；意圖差異與必要知會另立段落 |
| 13 | 報告帶 meta | 報告開頭放 YAML meta（日期、作者、遠端連結、票號等），值取自 `task_plan.md`「報告 meta」 |

完整說明：`references/rules.md`
