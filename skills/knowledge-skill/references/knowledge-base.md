# 公用知識庫寫入規範（單一規範來源）

跨專案共用的**可重用經驗**，以 MADR（Markdown Architectural Decision Records，欄位繁體中文化）格式記錄，供所有任務參考。本檔為知識庫格式、收錄判準、覆蓋／停用機制與索引流程的**唯一規範來源**；`knowledge-tools-skill` 與本 skill 的其他文件均指向此處。

> 📌 `knowledge-record-skill/SKILL.md` 不再內嵌本檔的副本：範本取自 `assets/knowledge.md`（由 `kb-new.sh` 讀取），完整收錄判準指向本檔「三」，只在自身保留一段速判規則。改動「三」時要確認該速判規則仍相容。三個 skill 因此需並存安裝。

> 📍 **位置**：公用知識庫不在專案內，預設位於 `$HOME/.knowledge-skill/knowledge/`，可用設定檔 `~/.config/knowledge-skill/config` 或環境變數 `KNOWLEDGE_BASE_DIR` 覆寫（環境變數優先）。所有掛載的專案共用同一份。

## 一、分類目錄

知識檔依分類歸檔，不扁平存放：

- **頂層分類（6 類）**：`ui` / `ux` / `dev` / `ops` / `data` / `else`。
- **第二層**：依語言／框架／平台細分，例如 `dev/php-laravel/`、`dev/ai-llm/`、`ops/cloudflare/`、`data/ai-llm/`。
- 路徑形如 `{分類}/{語言-框架}/檔名.md`；無合適第二層時可直接放分類根（如 `else/檔名.md`）。
- 索引以**相對 `knowledge/` 的路徑**登錄。

## 二、MADR 知識檔格式

範本：`assets/knowledge.md`。`標題` 與 `觸發時機` 置於上方 front matter（meta），其餘為 MADR 段落。

```markdown
---
標題: [知識主題]
觸發時機: [何時應參考此知識；一行寫清楚，供索引比對]
取代: -
被取代於: -
狀態: 人工審核確認
---

## 摘要
[一句話描述核心結論]

## 脈絡與問題陳述
[背景與要解決的問題]

## 決策驅力
-

## 考量選項
- [選項 A]
- [選項 B]

## 各選項利弊
-

## 決策結果
[選擇哪個選項與理由]

## 影響
[好處 / 壞處]

## 驗證
-

## 補充資訊
[來源任務、參考連結]
```

- front matter 五欄：`標題`、`觸發時機`、`取代`、`被取代於`（這兩者預設 `-`）、`狀態`。
- `取代` / `被取代於` 填**相對路徑**（含分類目錄），由 `kb-supersede.sh` 自動維護，勿手填。
- `狀態` 分兩層，由腳本維護，勿手填：
  - `AI 自動確認`：`knowledge-record-skill` 免詢問自動收錄、尚未經人工審核的知識（`kb-promote.sh --auto` 寫入）。
  - `人工審核確認`：使用者同意後記錄，或審核過自動收錄的知識（`kb-promote.sh --yes` 寫入；`kb-auto.sh confirm` 由前一層轉換）。
  - 沒有 `狀態` 欄的是這個欄位出現前寫入的知識，視為 `人工審核確認`；`kb-health.sh` 會回報缺欄位，`kb-repair.sh` 補上。
- `決策驅力`、`各選項利弊`、`驗證` 三段預設保留一行 `-`，由使用者視需要補充。
- 索引欄位（`觸發時機`、`摘要`）由 `kb-reindex.sh` 解析 front matter 的 `觸發時機:` 與 `## 摘要` 段第一行，務必各自第一行就寫清楚。

## 三、何時產生知識檔案

✅ **需要記錄**：
- 使用者明確指定要記憶的原則、規則或習慣（如命名慣例、檢查流程）
- 使用者要求「記住」、「以後都這樣做」等指令
- 跨專案可重用的工作方法或解決方案
- 透過互動修正後發現、未來仍適用的重要事項

❌ **不需要記錄**：
- 一般常見的程式設計知識
- 框架標準用法
- 已在官方文件中說明的內容
- 僅適用於單一專案或單一任務的一次性指令
- **流水帳**：本次改了哪些檔案、跑了哪些指令、依序做了哪些步驟

> ⚠️ 知識庫跨專案共用，記錄前先判斷該知識**換到別的專案是否仍成立**。只對當前專案成立的細節（特定檔案路徑、特定服務設定）不應寫入。

> ⚠️ 過程紀錄屬於任務資料夾的 `notes.md`，不是知識。只有從過程萃取出的「下次遇到同情境該怎麼做」才寫進知識庫；萃取不出來就不寫。

## 四、讀取知識（每個階段開始前必做）

索引分兩層，**逐層下探，不要一次讀完整棵樹**：

1. 讀取頂層 `$KNOWLEDGE_BASE_DIR/index.md`（預設 `$HOME/.knowledge-skill/knowledge/index.md`）——只有分類目錄與各分類的知識標題
2. 依當前階段內容比對分類與標題，判斷可能相關的分類
3. 有命中才讀該分類的子索引 `{分類}/index.md`，裡面才有完整的「觸發時機」與「摘要」
4. 確認觸發時機相符，才依子索引的相對路徑讀取知識檔
5. 提示使用者：
   - 有載入 → `📚 已參考公用知識庫：knowledge/<相對路徑>`
   - 有載入，且子索引的 `狀態` 欄是 `AI 自動確認` → `📚 已參考公用知識庫（AI 自動確認，尚未人工審核）：knowledge/<相對路徑>`。這類知識照常採用，註明是讓使用者知道它派上用場，可以趁機確認或刪除
   - 無匹配 → `📚 公用知識庫無相關項目`

> 分兩層是刻意的：頂層行數只隨分類數成長，不隨知識檔數成長，每個階段開始前的固定讀取才不會隨知識庫變大而持續吃掉 context。

## 五、建立知識（不手動編輯 index.md）

固定流程交由 `knowledge-tools-skill` 的腳本完成，代理只負責判斷內容與選擇分類：

1. 依收錄判準篩出可跨專案重用內容。
2. 選擇分類目錄，決定 `{分類}/{語言-框架}/[topic].md`；相同主題合併進既有檔，不重複建檔。
3. **新主題**：先產草稿（腳本會擋掉路徑不合法與目標已存在，並複製 `assets/knowledge.md`）：
   ```bash
   sh <knowledge-tools-skill>/scripts/kb-new.sh <相對路徑>
   ```
4. 填寫草稿內容（`標題`、`觸發時機` 與 `## 摘要` 第一行務必寫清楚，索引只取這幾處）。
5. **安裝**（驗證格式、拒絕覆蓋、原子寫入，並自動重建索引）：
   ```bash
   sh <knowledge-tools-skill>/scripts/kb-promote.sh <草稿路徑> <相對路徑> --yes --source "<來源說明>"
   ```
   合併進既有檔則改為直接編輯該檔，再執行 `kb-reindex.sh` 重建索引。
6. 提示使用者記了什麼、在哪裡：每則列出知識庫內的相對路徑與摘要第一行（格式見 `knowledge-record-skill/SKILL.md` 步驟 7）

> `--yes` 代表**同意已取得**，不是略過同意；未徵詢前不得帶。手改 `index.md` 一律禁止。
>
> `knowledge-record-skill` 的免詢問自動收錄改帶 `--auto`（不可與 `--yes` 並用）：腳本自行確認自動收錄開關開啟、`## 驗證` 段有內容，並把狀態寫為 `AI 自動確認`。何時可以走這條通道見「八」。

## 六、覆蓋／停用機制（新舊知識矛盾）

當新知識與既有知識**矛盾**（同一觸發情境給出相衝突的決策結果）時：

1. **比對**：可用 `kb-reconcile.sh [分類前綴]` 列出生效知識輔助判斷。
2. **呈現並取得同意**：把矛盾項與處理建議呈現給使用者，**取得明確同意後**才停用舊知識。
3. **執行取代**（由腳本確定性完成）：
   ```bash
   sh <knowledge-tools-skill>/scripts/kb-supersede.sh <舊檔相對路徑> <新檔相對路徑> --yes
   ```
   腳本會在雙方 front matter 寫入取代關係、把舊檔移入 `deprecated/`（鏡像分類路徑），並重建兩份索引。
4. 停用後的決策保留在 `deprecated/`，索引登錄於 `deprecated/index.md`（含「被取代於」），供日後追溯。

`knowledge-record-skill` 建檔時，舊知識若只是**過時**或**原本就錯**（有本次驗證的事實佐證），不算矛盾：直接改寫舊檔或取代，不詢問，事後回報；拿不準時當矛盾處理。做法見 `knowledge-record-skill/SKILL.md` 步驟 6。

## 七、索引結構（兩層）

所有索引皆由 `kb-reindex.sh` 確定性產生，代理不手改。索引是各裝置可自行重建的衍生物，**不參與雲端同步**：`kb-reindex.sh` 會把各層 `index.md` 標記為 Dropbox 忽略（macOS），避免多台裝置先後覆寫而產生衝突複本。因此在共用知識庫的其他裝置上缺 `index.md` 是常態，執行 `kb-reindex.sh` 重建即可（六個分類目錄齊全時不需先有 `index.md`）：

**生效**

- **頂層** `knowledge/index.md`：`## 分類目錄` 表格，欄位 `| 分類 | 筆數 | 知識標題 |`。分類欄是反引號純文字（如 `` `dev/php-laravel` ``）而非 Markdown 連結——索引解析器把「第一欄有連結」的列一律視為一筆知識，做成連結會讓每個分類被誤算成知識檔。
- **分類子索引** `knowledge/{分類}/index.md`：欄位 `| 知識 | 觸發時機 | 摘要 | 取代 | 創建時間 | 更新時間 | 狀態 |`，第一欄為 `[標題](檔名)`，**連結相對該分類目錄**。
- 直接放在知識庫根目錄、不屬於任何分類的知識檔，列在頂層的 `## 未分類知識` 表（欄位同子索引）。這是防止漏登錄的保險，不是建議做法——`kb-health.sh` 會以 `invalid_category` 標記這類檔案。

**停用**

`knowledge/deprecated/` 下為同構的兩層：頂層 `deprecated/index.md` 是分類目錄，`deprecated/{分類}/index.md` 欄位為 `| 知識 | 觸發時機 | 摘要 | 被取代於 | 創建時間 | 更新時間 |`。

**創建時間與更新時間**

兩欄只存在子索引（含 `## 未分類知識` 與 `deprecated/`），知識檔不帶這兩個欄位，格式為 `YYYY-MM-DD HH:MM:SS`（本機時間）：

- **更新時間**：知識檔的最後變更時間（mtime），每次 reindex 重新讀取。
- **創建時間**：只存在索引裡，`kb-reindex.sh` 每次重建都會從舊索引讀回沿用；取代搬進 `deprecated/` 時以對應路徑沿用原值。找不到舊值時：
  - 舊格式索引已登錄、但還沒有時間欄（本機制上線前的知識）→ `1970-01-01 00:00:00`
  - 舊索引存在但沒登錄這份（剛建立，或從其他位置同步過來後第一次登錄）→ 重建當下的時間
  - 整份頂層索引不存在（新裝置、索引被移除）→ `0000-00-00 00:00:00`

因為索引不參與雲端同步，創建時間是**各裝置各自的紀錄**：同一份知識在不同裝置可能顯示不同的創建時間。

**狀態欄**

只有生效清單有（子索引與 `## 未分類知識`），停用清單沒有。值取自知識檔 front matter 的 `狀態`，沒有此欄的知識顯示 `人工審核確認`。這一欄固定排在最後：其他工具以欄位位置讀取前面幾欄，新增欄位只能往後加。

**筆數欄的作用**

頂層帶「筆數」不只是給人看：tray 的狀態快取只 stat 頂層索引，靠筆數欄的變動偵測整棵樹的新增／刪除，不必逐一 stat 每份子索引。調整頂層格式時不可移除此欄。

## 八、互動式知識記錄

`knowledge-record-skill` 可由模型自動觸發，但**寫入前須取得同意**：使用者明確要求保存（「記住」「以後都這樣做」等）視為同意，直接記錄；其餘偵測到候選時以選單呈現，讓使用者選要記哪幾則。唯一不經同意就新增知識的情況是下面的免詢問自動收錄。

```
📚 偵測到可能需要記錄的偏好/原則：
- [k1] [描述內容]

是否記錄至公用知識庫？回覆 k1 確認，或輸入 n 跳過。
```

原生選單工具（`AskUserQuestion`／`request_user_input`）可用時改用原生選單，上述文字編號只是 fallback。

選單另有「本 session 都記錄」：一次同意本 session 後續的候選，但只涵蓋記錄、不涵蓋衝突的取代，每次寫入仍回報；開新 session、compaction 或使用者撤回後失效。細節見 `knowledge-record-skill/SKILL.md` 步驟 4。

**免詢問自動收錄**（預設開啟）：代理自己判斷出的候選，五條閘門全過才不徵詢、直接寫入——全新且無重複、跨專案通用、本次實際驗證過、沒有這則脈絡會做錯、不含敏感內容。任一條不過就照上面的選單徵詢。這條通道只新增知識，不合併、不改寫、不取代；同一次任務最多 10 則；寫入的知識狀態為 `AI 自動確認`，每次都回報。使用者可用 `kb-auto.sh off --yes` 關閉、`kb-auto.sh confirm` 把審核過的改為 `人工審核確認`。完整條件見 `knowledge-record-skill/SKILL.md` 步驟 4。

取得同意（或通過免詢問閘門）後依「五、建立知識」流程記錄，回報列出每則知識在知識庫內的相對路徑與摘要第一行，並提示刪除與確認的說法（格式見 `knowledge-record-skill/SKILL.md` 步驟 7）；使用者要移除則走 `kb-delete.sh`，不手動刪檔（索引需重建）。
