# 關鍵原則

本文件描述執行任務時的核心原則與反模式。

---

## 路徑描述規範

報告或檔案中描述路徑時，**一律以專案根目錄作為相對位置**。

✅ 正確：`src/services/config-service.ts`
❌ 錯誤：`/Users/<使用者>/example-project/src/services/config-service.ts`

**例外：任務完成時的對話輸出。** 上述規範適用於報告與檔案內文。任務完成時回報 `report-<任務名稱英文>.md` 位置屬對話輸出，需同時給出絕對路徑（供使用者複製開啟）與專案相對路徑（供貼進文件引用），格式見 `SKILL.md`「任務完成後」步驟 5。

---

## 報告改寫規範

`report-<slug>.md` 是**交付物，不是變更日誌**。分階段任務跨 session 續作、或使用者要求修正時，同一份報告會被改寫多次；第二次以後的改寫**一律以當前最後結論重寫對應段落**，不把每次變更依序追加成流水紀錄。被推翻的中間過程留在 `notes.md`，不進報告。

### 例外：獨立段落記錄，不混進正文結論

| 例外 | 判準 | 寫法 |
|------|------|------|
| **意圖差異** | 關鍵內容的前後意圖不一致——結論轉向、推翻先前決策、範圍明顯縮放 | 獨立段落「結論變更」：原結論／現結論／改變原因各一行 |
| **必要知會** | 與最終結論不衝突，但使用者必須知道——副作用、已知限制、未驗證項、被排除的做法 | 獨立段落「補充事項」：一項一行，寫明影響 |

判準：**只讀最終報告的人要能得到正確結論，且不會漏掉必須知道的事。** 需要回頭讀變更歷程才還原得出結論，就是寫錯了。

> 💡 同一原則在知識庫是「不收流水帳」（見 `knowledge-base.md` 三），在報告是「以最後結論為準」。

---

## 應避免的反模式

| 不要 | 改為 |
|------|------|
| 目標只說一次就遺忘 | 每次決策前重新讀取計劃 |
| 隱藏錯誤並重試 | 將錯誤記錄到計劃檔案 |
| 將所有內容塞入上下文 | 將大量內容儲存在檔案中 |
| 立即開始執行 | **先**建立計劃檔案 |
| 先標記完成再記錄發現 | **先** notes.md **再** task_plan.md |
| 將發現直接寫入報告 | 先記錄 notes.md，再整理成報告 |
| 報告逐次追加變更紀錄 | 以最後結論改寫；意圖差異與必要知會另立段落 |

## 待辦事項連動

待辦事項與 `task_plan.md` 可連動使用：

1. **記錄來源**：確保 `prompt.md` 有正確記錄任務來源與原始需求
2. **建立對應**：待辦事項的每個項目對應 `task_plan.md` 中的一個階段
3. **同步更新**：每個待辦項目完成時，同時更新 `task_plan.md`
   - 標記待辦項目為 completed
   - 編輯 `task_plan.md` 標記 [x]
4. **記錄發現**：完成階段後，將發現記錄在 `notes.md` 和 `knowledge/`

```bash
# 階段完成時的動作（順序重要！）
1. Write/Edit notes.md       # 第一步：儲存發現（避免遺忘）
2. Mark todo as completed    # UI 層面
3. Edit task_plan.md         # 持久化層面（標記 [x]、更新狀態）
4. Write knowledge/[topic].md  # 如有需要，建立知識檔案
5. sh kb-reindex.sh            # 由腳本重建兩層索引（不手改 index.md）
```

> 💡 **記憶口訣**：「先記後標」— 先記錄發現，再標記完成。

這樣可以：
- 在 UI 上即時看到進度
- 在檔案中保留完整記錄供後續 session 參考

## 啟動提問與計畫確認

任務開始前，需要使用者裁決的問題**以選單呈現、用選擇作答**，避免要求使用者用一段自由文字一次回覆全部設定。流程：先彙整五題預設值，用單一選單詢問「全部採用預設 / 逐項調整」；選「逐項調整」才對各題逐一以選項選單詢問，使用者只調整想改的項目、其餘維持預設。對應 `SKILL.md`「任務開始前」步驟 1，規範如下：

### 呈現方式

- Claude Code 的 `AskUserQuestion` 可用時必須呼叫；Codex 的 `request_user_input` 可用時必須呼叫。
- 依工具是否存在判斷，不把 Plan mode 當成唯一條件；Codex Default mode 若使用者自行啟用 `default_mode_request_user_input`，同樣可使用原生選單。
- 原生工具不可用時，先說明 client 限制，再以**編號選項清單**呈現。
- 每題最多三個固定選項；超過三項拆成兩層。無上限清單逐筆詢問「選擇此項／下一項／取消」。
- 原生工具可用時，不得要求使用者輸入固定選項的編號、label 或命令名。
- 只有選擇「自行輸入／自訂／要求調整」後，才要求自由文字。
- 每題標明預設；每個選項提供一行影響說明，建議選項排第一。
- VSCode extension panel 可顯示圖形化選項；VSCode integrated terminal 與獨立 CLI 使用 TUI。
- 非互動模式不承諾顯示選單；skill 不自動修改 client feature，也不以 MCP／Plugin 模擬一般提問。

### 大型選單與決策點

- **七項以上功能**：先分成最多三個群組，再於群組內選擇。
- **候選知識**：一項用「記錄／略過／本 session 都記錄」；多項先問「全部記錄／逐項決定／全部略過／本 session 都記錄」（此題例外為四個選項）。概括同意的範圍與失效條件見 `knowledge-record-skill/SKILL.md` 步驟 4。使用者明確要求保存時不跳選單，只有「這個」指向不明才詢問。
- **無上限檔案清單**：逐筆顯示摘要，提供「選擇此項／下一項／取消」。
- **路徑無法讀寫**：使用原生三選一；選擇「指定其他路徑」後才收自由文字。
- **研究計畫**：使用「批准並繼續／要求調整」；只有選擇調整才收意見。
- **分階段接續**：使用「繼續下一階段／本次停止」。
- **新舊知識取代**：使用「以新知識取代／保留舊知識」，同意後才傳 `--yes`。只用於衝突；舊知識過時或原本錯誤時直接改寫，事後回報。

### 五題選項規範

1. **票號／編號**（決定任務名稱前綴）：
   - 先嘗試從 git 分支名稱、目錄結構或對話上下文**推斷**可能的票號（如 `feat/T-0001-xxx` → `T-0001`）。
   - 提供選項：〔推斷票號：`<推斷值>`〕（僅在能推斷時提供）／沒有票號／自行輸入票號。
   - 有票號則組成 `票號-任務名稱`；轉換規則見 `file-structure.md` 的「任務命名規則」。
2. **執行模式**：(A) 一次完成 / (B) 分階段執行 / (C) 部分執行（見下方「分階段任務執行規範」）。任務複雜或需跨多個觀察系統研究時，主動建議 (B)。
3. **報告保存路徑**：顯示預設 `<工作區>/docs/knowledge-skill/<任務名稱>-<流水號>/`。
   - 使用預設 → 直接以目前工作區作為 `<工作區路徑>`。
   - 自訂 → 使用者輸入的路徑作為 `init-session.sh` 的 `<工作區路徑>`（報告仍落在該路徑下的 `docs/knowledge-skill/`）。
   - **若更改了路徑**：設定完成後詢問是否將此偏好寫入公用知識庫，供後續任務沿用；使用者同意才依「任務完成後」流程記錄。
4. **是否先確認研究計畫**：(否) 直接執行 / (是) 先補上詳細研究動作計畫並等待確認。
5. **作者**（寫入報告 YAML meta）：
   - 讀取工作區的 `git config user.name` 作為預設。
   - 提供選項：〔git user.name：`<值>`〕（僅在讀得到時提供）／自行輸入作者。

五題的結果（報告保存路徑除外）填入 `task_plan.md` 的「報告 meta」區塊，建立報告時原樣複製到報告開頭；欄位見 `file-structure.md` 的「報告 YAML meta」。

### 研究計畫確認流程（選擇「是」時）

1. 完成 `SKILL.md` 步驟 4（編輯 `task_plan.md`）後，在 `task_plan.md` 的「研究動作計畫」區塊補上**具體**的研究步驟、預期查閱來源與每步的驗證點。
2. 將該計畫呈現給使用者，依原生路由詢問「批准並繼續／要求調整」。
3. **未取得確認前，不要展開完整研究與報告**。
4. 使用者要求調整 → 修改 `task_plan.md` 後再次呈現，直到同意為止；同意後才繼續後續階段。

## 分階段任務執行規範

當任務較為複雜，可能需要多次對話才能完成時，應提供分階段執行的選項。執行模式已於「啟動提問」一次取得，此處說明後續處理。

### 執行模式選項

啟動提問中「執行模式」的三個選項：

```
(A) 一次完成全部任務
(B) 分階段執行（每次完成後暫停，下次對話繼續）
(C) 僅執行部分任務（請指定項目編號，如：1,3,5）
```

編輯 `task_plan.md` 時，在「執行模式」欄位記錄使用者選擇。

### 分階段任務：每次對話開始時

> 適用於選擇「分階段執行」(B) 的任務

1. **讀取進度**：
   - 讀取 `task_plan.md`，檢查未完成的任務項目（`[ ]` 標記）
   - 讀取 `notes.md`，找到對應階段的上下文與進度

2. **提示目前狀態**：
   ```
   📌 繼續執行任務：[任務名稱]
   ✅ 已完成：[已完成項目數] / [總項目數]
   🔜 接下來：[下一個未完成項目]
   📄 上次進度：[notes.md 中的最後記錄摘要]
   ```

3. **確認後繼續**：依原生路由詢問「繼續下一階段／本次停止」，確認後再執行下一個未完成項目

### 部分執行模式

> 適用於選擇「僅執行部分任務」(C) 的任務

1. 在 `task_plan.md` 標記本次要執行的項目（如加上 `🎯` 標記）
2. 僅執行被標記的項目
3. 完成後依原生路由詢問「繼續其他項目／本次停止」

### 注意事項

- 每次對話結束前，**必須更新** `notes.md` 和 `task_plan.md`
- 記錄足夠的上下文，讓下次對話能順利接續
- 若任務有相依性（任務 B 依賴任務 A 的結果），需在 `task_plan.md` 中標註
